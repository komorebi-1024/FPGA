## 3 我已核查出的关键技术事实

这些发现决定今晚如何节约时间。

1. **首选工程已经有主要基础链路。** `lab_ex5_i2s` 的顶层连接了读图、SDRAM 双缓冲、按键消抖、自动播放、I2S 测试音及 HDMI 发射 IP。应先跑通它，再逐项改，不要从零写 HDMI 编码器。
2. **图片读取不等于完整 FAT32 文件读取。** `bmp_read.v` 实际扫描物理扇区中的 BMP 头，然后连续读后续扇区。没有看到根据目录文件名、FAT 簇链定位文件的完整实现。文件碎片、物理存放位置、旧数据残留都可能影响结果，文件名排序不能保证播放顺序。
3. **当前只扫描前 64 MiB。** 顶层把扇区范围设为 0～131071，按每扇区 512 字节计算。文件起始位置超出范围会找不到，不能靠“卡上能打开图片”证明 FPGA 能读到。
4. **先用正好四张标准测试图。** 工程目标计数为 4，找到四张便可结束扫描；只放一张可能继续扫到边界，造成启动等待。源码对正高度 640×480、24 位、非压缩 BMP 进行匹配，先使用正常 bottom-up BMP，再检查显示方向。
5. **原卡同步脚本会改写并删除数据。** `sync_to_sd.py` 会破坏当前可见 BMP 的头并递归删除目标盘目录，而且在检查新图片是否存在之前就进行清理。它不能清除所有早已删除的历史扇区，也不保证文件连续。因此，后续只能在确认并备份的专用 TF 卡上安排受控准备，不直接让新手照抄一个盘符运行。
6. **双缓冲有基础，但不能仅凭名字断言绝不撕裂。** 原读缓存地址在帧读取请求时锁定，写完后发布新的缓冲索引。新增控制要区分“请求下一张”“写入完成”“新帧真正显示”，并确保旧缓冲未释放前不被覆写。按键突发、提交边界和跨时钟域都需要检查。
7. **自动轮播的标称一秒不一定是完整切图周期。** 原计数在没有加载任务时才运行，因此实际间隔还包含加载时间。我们要定义“显示驻留时间”，参数调整只改计时逻辑，不能把 `CLK_FREQ_HZ` 改错来凑秒数，否则消抖时间也会受影响。
8. **48 kHz 的文字说明与 PLL 参数有小偏差。** HDMI IP 配置为 `48K`，而音频 PLL 文件给出的输出约为 12.295082 MHz，发生器按 256 个主时钟形成一组左右声道样本，推算约 48.0277 kHz。它是标称 48 kHz 通路，不能写成已经测得精确 48.000 kHz。后续要结合 PLL 可实现频率、ACR 和接收端表现判断是否调整。
9. **音频模块不应按文件名或旧注释猜。** 当前产生的是循环音阶测试信号，`PHASE_INC` 参数在这个版本中没有被使用；只改它不会得到预期的新音调。语音 ROM 文件存在，但在当前工程中被排除，不能声称已经能播报站名。
10. **音频版与视频版的复位处理不同。** 音频顶层复位主要受外部复位和音频 PLL 锁定控制；视频版本额外等待系统、视频 PLL 稳定。应在复制工作副本后检查并设计统一复位，不应盲目整文件替换。
11. **已有 `.bit` 只作参考。** 两个目录中都有历史编译文件，且视频目录还留有不同名字的旧运行目录。最终交付必须记录本次源码对应的编译时间、日志和编程文件，避免拿到错误的旧版本。
12. **TD 安装目录存在。** 找到 `D:\Anlogic\TD_6.2.1_Engineer_6.2.168.116\bin\td.exe`。尚未启动或确认许可、驱动及运行状态，也未确认可用仿真器。不能因此省略第一轮环境验证。

## 4 用最简单的话理解系统

你可以把它理解成“仓库、两块画板、画面播出和声音播出”。

- TF 卡是素材仓库，里面放四张图片。
- BMP 解析器把文件里的字节变成红、绿、蓝三个颜色数值。
- SDRAM 有两块画板：一块给屏幕读，另一块准备下一张。准备完成后，在合适的帧边界交接。
- HDMI 输出按固定节奏把像素送给显示器，即使图片内容不变，也必须不停输出。
- 音频模块持续提供采样点，HDMI 发射模块把它们和图像一起传出去。
- 场景控制器决定“现在到哪站、下一站是什么、是否自动展示、何时响提示音”。

```text
TF 卡 → SPI 读取 → BMP 解析 → 写缓存 → SDRAM → 读缓存 → 动态文字合成 → HDMI 视频
按键 → 消抖 → 场景控制 → 请求加载图片
                         ↑ 新图片正式显示的确认
                         └→ 更新站名、模式和到站事件
到站事件 → 提示音控制 → I2S 音频 → HDMI 音视频发射 → HDMI_B
```

明白五个词就可以开始：

| 词 | 对你而言是什么 |
| --- | --- |
| Verilog / `.v` | 描述硬件怎么工作的源代码，不是按一行一行顺序运行的普通脚本 |
| 顶层 `top` | 把其他模块接在一起的总接线图 |
| `.adc` 引脚约束 | 把代码端口对应到芯片引脚，再对应到板上的按钮、接口 |
| `.sdc` 时序约束 | 告诉工具各时钟多快，以及哪些路径需要怎样检查 |
| 综合、布局布线、位流 | 把代码变成硬件结构，再安排在芯片中，最后生成可以下载的配置文件 |

仿真相当于在电脑里模拟按钮、时钟和画面事件；它能验证逻辑，但不能替代真实 TF 卡、HDMI 设备和电源条件的测试。

## 5 今晚的功能设计与文件分工

建议四张图片分别对应四个演示站，例如校门、图书馆、实验楼、体育馆。所有名称都可换成你们学校实际地点。保持四张都符合基础格式，站点顺序以实际图片索引映射为准，首次上板再确认扫描顺序。

先采用下面的交互，避免操作过多：

- 原逻辑 `key1`：下一站或下一张；在场景模式下提出到站请求。
- 原逻辑 `key2`：启动或停止自动展示，保留基础要求。
- 自动展示按设定驻留时间换图；手动到站可暂停自动展示，显示下一站页面，提交后显示到站信息。
- 再次启动自动展示表示恢复行驶中的文旅展示。今晚先用同一组四站图片，不另加多路线素材体系。
- 程序内部参数配置 3、5、8 秒等驻留时间，默认 5 秒。有余量再接实际开关做运行时配置。
- OSD 的站名随“真正显示的图片编号”变化，不能在用户刚按按钮时就提前更新。
- 音频保留独立可选的基础测试音模式；到站模式使用短提示音，并保持连续有效的音频采样流，静音时发送零样本，不随意停止时钟。

代码端口不等于板上标签：现有约束 `key1=B2` 对应手册 KEY2，`key2=C1` 对应 KEY4，`rst_n=A2` 对应 KEY1。手册中 KEY3 在 B1。正式接线时以队友板卡版本和原理图复核。

| 计划修改或新增 | 负责什么 | 优先级 |
| --- | --- | --- |
| 原 `top_tf_hdmi_audio.v` | 连接新模块、时钟、复位及视频音频通路 | 必做 |
| 原 `SD/sd_card_bmp.v` 和相关缓存控制 | 轮播参数、图像索引导出、加载与显示提交的接口；必要的可靠性修正 | 必做 |
| 拟新增 `station_ctrl.v` | 当前站、下一站、自动/手动状态、请求与确认 | 必做 |
| 拟新增 `osd_overlay.v` 与小型字模 ROM | 在像素流上叠加站名/站号、模式、运行秒数 | 首选扩展 |
| 拟新增 `arrival_audio_ctrl.v` | 到站事件转成一次提示音，处理跨时钟域 | 次选扩展 |
| `tb_station_ctrl.v` 等局部测试 | 模拟按键、加载延迟、提交确认和复位 | 必做 |
| 素材清单、图片生成/检查工具 | 确认尺寸、色深、压缩、序号和方向 | 必做 |

这些名字是设计计划，最终实施中可以根据原模块接口调整。

OSD 应在 SDRAM 读出 RGB 之后、进入 HDMI 视频流转换之前合成。只对规定的像素区域换成字符颜色，背景其他像素照常通过。初版用固定位置的不透明字，不做 Alpha 混合和滚动。字模只存实际需要的汉字、数字，空间小，容易验证。若汉字耗时超预算，先保证动态站号和秒数正常；这能证明实时叠加，但不能把更完整的滚动字幕效果写成已实现。

双缓冲按照当前每像素 32 位存储估算：单帧 `640×480×4=1,228,800` 字节，两帧约 2.34 MiB。芯片资料给出 SDRAM 为 `2M×32bit`，即 8 MiB。容量上有空间，但控制器带宽、IP 使用和时序仍要检查，不可仅凭容量推断稳定运行。

### 第 1 步 用半小时学会 TD 的基本流程

**你按什么顺序做：** 启动现有 TD；选择打开工程，定位工作副本内的 `src\td_project\HDMI1.4b_Transmitter_v1.0.al`；检查器件为 `EG4S20BG256`、顶层为 `top`；查看工程文件列表有无缺失；找到综合、布局布线和生成编程文件对应的流程节点。具体界面以你的 TD 版本为准，不另新建一个空工程重复添加文件。

**我怎么教：** 每次只解释当前需要的一项：先理解顶层，再看按键，再看图像和音频。你不需要先通读整本 Verilog 教程。

**完成标准：** 你能说清“代码 → 综合 → 布局布线 → 位流”的顺序，并知道本次输出到哪个 Runs 目录。

**常见卡点：** 缺许可、路径无效、缺 IP 或源文件。把第一个错误和附近日志交给我，不先批量修改一大串文件。

### 第 2 步 先编译未改动的工作副本

**为什么先做：** 如果原版在当前软件上都编译不过，后面改功能时就无法判断错误是环境还是新代码造成的。

**操作：** 运行综合和布局布线；成功后生成位流；保存完整日志、器件/顶层信息、资源占用、时序报告及输出文件时间。确认输入是刚复制的工程，不能把原目录旧 `.bit` 当本次结果。

**完成标准：** 有可以追溯到当前副本的编译结果；或者明确记录了首个环境问题及解决路径。布局布线完成也要看时序，不能只看“完成”。

**预算：** 首轮最多约 45 分钟。如果超时或环境不通，优先修环境，暂停扩展素材设计。今晚不能绕过厂商加密 IP 自行猜一个替代模块来声称全工程通过。

### 第 3 步 准备四张标准素材

**你做什么：** 决定四个站名和一句作品简介，提供自己有权使用的照片，或先接受简单的路线、建筑示意图。

**我做什么：** 生成或转换成标准 BMP；检查文件头，确认宽 640、高 480、24 位、非压缩和像素起始偏移；加入“上/下、左/右”的临时测试标记以检查方向；记录图片与站点的映射。

**完成标准：** 四张素材和一份清单齐全，电脑端可以正确打开。标准 54 字节文件头的这类 BMP 通常为 921654 字节，但不能只靠文件大小判定格式。

**注意：** PNG 改后缀不是 BMP。把站名画进 BMP 只算图片内容，不算 FPGA 动态字幕。今晚仅准备素材文件，不访问不在身边的 TF 卡。

### 第 4 步 看懂现有按键与轮播

**你看哪几个点：** `sd_card_bmp.v` 中按键如何消抖、下一张请求如何记录、自动开关如何翻转、图片序号如何循环。

**小练习：** 用自己的话解释：为什么一个按钮弹跳不会算成多次按下；为什么加载下一张需要时间；为什么当前图片必须继续显示。

**我做什么：** 把轮播驻留时间独立成清楚的参数，并说明参数单位；保留按键同步和约 20 ms 消抖。若要新的按键控制层，应统一处理按键事件，避免新旧两套逻辑同时消费一次按下。

**完成标准：** 仿真可证明开/关自动展示、手动下一张、序号回绕和所选驻留时间正确。时间仿真用缩短的测试参数，不改变真实硬件时钟定义。

### 第 5 步 加入最小站点状态机

**你理解什么：** 状态机就是“当前处于哪一步，发生什么事件后走到下一步”。可以先画四个方框：自动展示、等待新站图片、到站显示、恢复展示。

**我做什么：** 实现明确的请求、忙碌、完成确认；按键触发只提出加载请求；新帧正式显示后才更新当前站、下一站和到站事件。忙碌时只保留约定数量的请求，避免连按造成图片和文字脱节。

**完成标准：** 仿真中即使把图片加载延迟拉长，站名仍和实际提交的画面一致；最后一站能按约定回到第一站；复位后状态确定。

**排错方法：** 只观察 `requested_id`、`displayed_id`、`busy`、`frame_commit`、`arrival_event` 等关键量，不一开始盯整条 HDMI 波形。信号名称可随实现调整。

### 第 6 步 完成一项可展示的扩展

**首选做法：** 在不改变 BMP 文件的情况下，让 FPGA 在画面上生成当前站/下一站或站号、AUTO/MANUAL 和递增秒数。

**你要理解：** 屏幕由一行一行像素组成。坐标落在字符位置就选字符颜色，其余位置选背景图片。数字能变化，是因为硬件按当前状态选择字形。

**我做什么：** 设计坐标与 RGB/DE/同步信号一致的流水线；完成字模和叠加；检查上下左右边界；制作可在电脑检查的合成示意或仿真输出。示意图明确标记为示意，不能当硬件照片。

**完成标准：** 同一张背景图下秒数持续变化；站点提交后文字正确更新；不在有效区写入错误像素；像素时序与内容不发生错位。最终实物无闪烁要等下午确认。

**预算控制：** 先固定位置、不透明字符；有余量再加线路进度标记。不要同时做 FFT、缩放、淡入淡出三套扩展。

### 第 7 步 有余量再加到站音效

**你理解什么：** 48 kHz 是每秒样本数量，440 Hz 是音高，两个不是一回事。已有测试音能证明音频链路目标，但不是站名语音。

**我做什么：** 根据真正的到站画面提交事件，触发一次短提示音；跨时钟域用同步握手或翻转事件；逐声道检查有效样本；保证音频数据持续送入 HDMI。保留独立测试音模式用于下午排错。

**完成标准：** 仿真中一次到站只发出一个事件，持续时间可解释，复位和重复按键不会卡死；时钟和采样率计算有记录。实际听感和终端兼容性待上板。

**停止条件：** 影响视频基线或音频流稳定时，交付只保留已经验证的测试音版本，将提示音联动标为未完成。不要为了看似“完整报站”而临时加入未经验证的 TF 音频读写仲裁。

### 第 8 步 做真正有用的仿真

优先测试新写的场景逻辑、提交握手、计时和 OSD。厂商加密 HDMI/SDRAM IP 如果缺少可用仿真模型，采用接口替身测试周边逻辑，并明确这不等于整条硬件链路验证。

| 测试 | 输入条件 | 应当观察到 |
| --- | --- | --- |
| 复位 | 启动、运行中再次复位 | 状态、索引和事件标志回到规定值 |
| 手动下一张 | 单按、抖动、连续按 | 单次有效事件；请求策略固定；不越界 |
| 四图循环 | 持续产生加载完成 | 0→1→2→3→0，显示索引与文字一致 |
| 自动开关 | 播放中暂停、再启动 | 暂停时不自行切换，恢复后计时正确 |
| 驻留时间 | 两个不同配置值 | 按约定时间发出下一张请求 |
| 加载延迟 | 延迟、忙碌时按键、迟到确认 | 旧图继续显示，不提前改站名 |
| 帧提交 | 写完恰逢帧边界、快速连续请求 | 不重用正在显示的缓冲，不丢确认 |
| OSD | 字符区域边界、数字变化 | 背景保留，字形与像素坐标对齐 |
| 音频事件 | 单次与重复到站、复位 | 每次实际提交只触发规定次数 |

工具优先使用可用的 ModelSim/Questa；若本机没有可用安装，再评估轻量开源仿真器用于不含厂商原语的新增模块。今晚不因为整套商业仿真环境安装阻塞所有工作，但缺失的验证要真实记录。

### 第 9 步 集成编译并检查报告

**操作：** 新模块加入工作工程；先综合，处理第一个真实错误；再布局布线、查看时序和资源；最后生成位流。每次只合入一组功能，保留上一次成功版本。

**我重点看：** 缺文件、重复模块、位宽截断、多驱动、意外锁存器、未使用信号、时钟约束及跨域。原时序文件中把视频像素时钟和串行时钟设为 exclusive，需要结合实际同时工作关系和 IP 要求核查，不能为了清空违例而盲目增加 false path。

**完成标准：** 最终目录存在新生成的可追溯编程文件、完整编译日志及问题说明；不存在未解释的关键失败。若不能通过，最终状态必须写“编译未通过”，不使用历史文件伪装成功。

### 第 10 步 整理明早代码包

计划交付内容：完整 `.al` 工程、Verilog、IP 和字模/初始化数据、引脚及时序约束、四张素材、局部仿真、编译日志、生成的配置文件，以及下面四份文字材料。

1. `README_从这里开始.md`：工程怎么打开、器件和顶层、怎么编译、输出在哪里、当前完成状态。
2. `新手操作指南.md`：每次需要点击或检查什么，正确现象是什么，出错后收集哪几项信息。
3. `实现与验证记录.md`：从原例程复用了什么、自己实现了什么、仿真和编译结果、未验证项。
4. `下午上板验收表.md`：连接、TF 卡、下载、声音、切图、固化、冷启动、记录项。

源码与日志建议同时保留版本号和日期；配置文件记录校验值，确保队友拿到的是对应版本。工作目录可继续演进，交付目录冻结，避免下午拿错文件。

### 第 11 步 下午按检查表上板

这一步由你与队友实际操作。规划并不代表我已给队友发消息或安排了远程访问。

1. 确认板卡型号、供电、USB-JTAG 下载口与 HDMI_B。HDMI 连接电视或能播放 HDMI 音频的显示器，笔记本 HDMI 通常是输出口，不能直接当显示器输入。
2. 先用队友已验证的工程确认硬件连接；再用本项目编译文件做 SRAM/JTAG 下载。先排除线缆和接错口的问题。
3. 备份并确认专用 TF 卡；根据实际盘符、容量和文件物理布局准备四图。不能默认盘符就是 E，也不能未经确认清空存有资料的卡。若物理扫描读不到或顺序错，检查扇区、碎片和扫描范围，不先乱改 HDMI。
4. 检查四图方向、颜色、边缘和站点映射。初版扫描顺序以实测为准，必要时重新准备介质或修正映射。
5. 验证手动下一张、自动开始/停止、参数化周期；连续切换至少 20 次，记录有无闪黑、撕裂和卡死。
6. 在图像显示期间验证 HDMI 测试音；再验证到站联动模式。无声先查显示设备的 HDMI 音频能力、音量和静音，再查 I2S/ACR。若有逻辑分析仪或厂商调试手段，测 LRCK 或样本事件，确认采样率；没测就不要填精确值。
7. 验证动态叠加不依赖更换 BMP：停在一张图上，秒数仍更新，切站后站名对应。
8. 用 TD 下载工具选择配置 Flash 的 `PROGRAM FLASH` 模式，核实板卡配置器件与当前文件格式后运行并校验。旧手册对容量和 `.bit/.bin` 的说法不一致，最终以实际板卡及 TD 模式要求为准，不能把改扩展名当格式转换。
9. 彻底断电再上电，不重新下载，观察图片、按键和声音；至少重复 3 次。USB 可能同时供电，必须保证断掉所有实际供电后再恢复。TF 卡仍是媒体来源，固化程序不等于把图片也烧入 FPGA。
10. 连续运行至少 30 分钟，并做一次冷启动、四图、切换、声音、OSD 的完整演示录像。上述次数与时长是建议的内部验收标准，不是伪称官方规定。

**基础通过的证据：** 四图视频、按键与轮播视频、HDMI 声音记录、固化校验日志及不重新下载的冷启动录像。编译成功不能替代这些证据。

### 第 12 步 完成最终参赛文档

明早先形成准确的技术初稿；下午补实测截图和数据，再输出正式 Word/PDF 或学校要求的模板。

建议正文覆盖：作品名称和简介、需求对应表、系统结构、板卡与开发环境、图片读取与缓存、交互状态机、HDMI 音频、扩展模块、自主实现与参考例程对比、测试结果、操作说明、局限及改进、参考资料。

写文档的顺序是：需求表 → 架构图 → 实际模块 → 测试记录 → 简介和总结。这样不容易先写出还没实现的功能。

| 要写的结论 | 必须有的依据 |

| 支持四图显示 | 四张素材格式检查及实物播放结果 |
| 切换连续稳定 | 连续切换录像、次数与异常记录 |

## 9 明早交付前你应当能独立回答的问题

不要求你一夜成为 FPGA 专家，但应学会以下内容：

1. 我该打开哪个 `.al`，修改哪个工作副本？
2. 四张图从 TF 卡到屏幕经历哪些模块？
3. 为什么需要双缓冲，为什么不能边显示边覆盖同一张图？
4. 哪个实体按键是代码里的下一张和自动开关？
5. 为什么站名应该等图片真正提交后再更新？
6. 48 kHz 和提示音的音高有什么区别？
7. 哪一部分是我们新增的，哪一部分来自厂商？
8. 仿真、编译、上板分别证明了什么，还缺什么证据？
9. SRAM 下载和 Flash 固化有什么区别？
10. 如果下午出现黑屏、旧图、无声，先分别检查哪三件事？

你不需要独立手写复杂的 HDMI 协议；需要能操作工程、解释主要链路、识别问题所在，并知道向 AI 提供哪段代码与日志。
